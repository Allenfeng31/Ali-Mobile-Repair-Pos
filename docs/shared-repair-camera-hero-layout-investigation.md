## Current interaction architecture

### Entry type 1: Model Hub to Shared Repair Page

**SOURCE-INFERRED:** `resolveModelHubRepairPageMode()` owns Model Hub destinations. For a global shared route it emits:

```text
/repairs/phone/<repair>?brand=<canonical-brand-slug>&model=<canonical-model-slug>
```

It uses the Model Hub route parameters, which come from `fetchModelRepairTypes()`. That function and Shared Repair pages both read `fetchRepairCatalog()`, so their source-level catalogue authority is the same public-catalogue reader.

`resolveSharedRepairContext()` validates those canonical slugs against the candidate list and only creates selected state for an exact candidate pair. Generic peripheral candidates carry `brand.slug` and `model.slug` unchanged.

### Entry type 2: Shared Repair Page model list

The current generic and Camera hierarchy model builders initially create direct canonical booking URLs with `getSharedRepairBookingHref()`. However, `SharedRepairHierarchySections` rewrites every `bookingHref` to the current repair-page query when `genericSelectionPath` is supplied. The global Generic peripheral and Camera modules currently supply that property, producing the intentional Phase 2 selected-page intermediate step.

Before Phase 2A, the hierarchy used its supplied direct booking URL. Commit `71be34c` introduced the rewrite for Generic pages; commit `6a45660` passed the same rewrite path for Camera pages.

### Entry type 3: direct organic no-model entry

The current UX-correction prompt is a real anchor to `#shared-repair-model-selection`. It correctly reaches the hierarchy, but the current model-card rewrite makes the user return to the selected repair page before booking. The proposed contract removes that intermediate step by preserving the pre-existing `bookingHref` generated by the hierarchy builder.

## Huawei P30 investigation

### Source findings

**SOURCE-INFERRED:** `huawei` and `p30` are valid canonical slugs in deterministic Generic route and hierarchy tests. The Loudspeaker, Earpiece, Power Button, and Volume Button route tests all include a Huawei P30 fixture and assert that `brand=huawei&model=p30` resolves to a selected device with a canonical booking identity.

The Generic route candidate builder:

- includes every model of every phone brand except `iphone`, `apple`, `samsung`, `google-pixel`, and `oppo`;
- does not exclude Huawei;
- does not require the requested peripheral service to exist before including the model as a candidate; and
- only uses a missing service to suppress the card's display-price label.

Therefore, a missing Huawei P30 Loudspeaker or Volume Button POS repair is not, by itself, a reason for the resolver to show no selection. There is no separate Huawei hardware registry or normalized-name transformation in this Generic candidate path.

`resolveSharedRepairContext()` can produce the reported no-selection state for the supplied URL only if the request's candidate input does not contain the exact pair, contains invalid/duplicate candidate identity, or the query shape is invalid. The supplied query shape itself is valid and the local tests prove the exact pair is accepted.

### Root-cause conclusion

**SOURCE-INFERRED:** the code-level Model Hub and Generic Shared Page slug contract is aligned for Huawei P30. The reported browser result cannot be caused by a missing service alone.

**NOT PROVEN FROM SOURCE:** the current durable public-catalogue snapshot, tagged-cache state, rendered server input, or whether the manual browser page used a candidate list with Huawei P30 missing or invalid. Those runtime values were deliberately not queried. The manual failure is therefore a blocking contract observation until a deterministic same-catalogue integration test and browser recheck reconcile it.

### Required invariant and test seam

If a Model Hub exposes a shared-repair link for `(brandSlug, modelSlug, repairSlug)`, the same catalogue snapshot must yield a Shared Page candidate with that exact `(brandSlug, modelSlug)` pair. Otherwise the Model Hub must not expose that shared-repair option.

The required future regression test should build one deterministic catalogue containing Huawei P30, run both `resolveModelHubRepairPageMode()` and the relevant Generic route candidate/selection construction, follow the emitted href, and assert selected-device state rather than `Select your model`. Include missing-model, duplicate-candidate, alias, stale-snapshot, and service-missing cases.

## Model-card destination revision

### Generic peripherals

Affected services are Loudspeaker, Earpiece, Power Button, and Volume Button.

- Current destination: `SharedRepairHierarchySections` rewrites each card to `/repairs/phone/<service>?brand=<brandSlug>&model=<modelSlug>` when `genericSelectionPath` is present.
- Original direct-book capability: `buildGenericPeripheralRepairHierarchyModels()` already constructs `getSharedRepairBookingHref()` for each card.
- Proposed destination: preserve that existing canonical booking URL instead of applying the page-query rewrite.

This is feasible without changing `publicBookingSelection.ts`, `cartAutoSelect.ts`, or `virtualCameraLens.ts`. The booking helper includes `category=phone`, display brand/model/service, and canonical `brandSlug`, `modelSlug`, and `serviceSlug`. Phase 1 then resolves that identity and keeps Cart pricing authority separate from display pricing.

### Camera modules

- Current destination: Front/Back Camera pass `genericSelectionPath={canonicalPath}`, so their hierarchy cards also reload selected query state.
- Proposed destination: retain the Camera hierarchy builder's existing `getSharedRepairBookingHref()` output.

The same Phase 1 safety argument applies. Camera model cards already have display-price labels derived by the Camera hierarchy builder, but the booking handoff still resolves canonical identity and price authority independently.

### Pixel V2

`SharedRepairPageV2ModelSections` currently routes the four migrated peripheral repair slugs to `?model=<slug>` through `SERVER_SELECTED_DEVICE_REPAIRS`; other Pixel model cards already use `getSharedRepairBookingHref()`.

The proposed direct-book rule is feasible using that existing helper while preserving Model Hub selected query state through `resolveModelHubRepairPageMode()`. The affected production implementation seam is `SharedRepairPageV2ModelSections.tsx`; its focused tests must change with it. Model Hub routing and the server-selected flow should not be repurposed for a list-card click.

### Camera Lens, Samsung, and OPPO

The two-entry-path rule is conceptually compatible:

- Model Hub: selected Shared Repair Page query state.
- Shared Page model list: direct canonical booking identity.

Do not promote that rule into Phase 2D while its known Lens blockers remain unresolved. Camera Lens has its own landing-page/model-list implementation, and its current dirty work is outside this investigation. Samsung and OPPO must be audited through their own adapters before changing any destination; no Phase 2D, 2E, or 2F source was changed here.

## Selected-model price requirement

### Current model-card display source

Generic and Camera hierarchy builders derive `priceLabel` only from a POS-origin repair using `resolveRepairDetailPricing()`:

- one trusted base or variant price: `$X`;
- multiple valid variants: `From $X`, where `X` is the lowest valid variant;
- absent/non-POS/invalid display price: no label.

The hierarchy model retains that already-derived label alongside canonical device identity. The selected-device view model currently does not carry it, so the Hero cannot display it.

### Recommended selected-Hero display contract

- Exact trusted display label: show `$X`.
- Multiple valid display variants: show `From $X`.
- No trusted display label: show no price line.
- Never substitute `Starting from $50`, `Custom Quote`, or `Quote on Request` as a model-specific Hero price.

This aligns with the current card-label policy. A future presentation-only extension can pass the selected hierarchy model's existing `priceLabel` into the selected Hero module by exact selected brand/model identity. It must not recalculate pricing or build a second authority.

### Phase 1 price safety

Direct booking is safe with the existing canonical helper. `resolvePublicBookingSelection()` resolves the canonical identity, and `resolvePublicBookingCartState()` keeps only `exact-pos`, `exact-pos-variant`, and the fixed Camera Lens exception as price authorities. Multiple variants and no trusted exact price remain quote-safe in Cart even if a model card displays `From $X`.

## Assessment card decision

The large `data-camera-module-assessment` block is local JSX in `CameraModuleRepairLandingPage`. It has no data dependency, state dependency, booking dependency, or schema dependency. Camera schema in this component is a BreadcrumbList built independently of the card.

The assessment-first concept is repeated in the camera route description/configuration, lower guidance, and call-ahead content, although the exact card text is not duplicated verbatim. Existing component tests explicitly assert `Quote only` and `Assessment before repair`, so a future removal/replacement must update those tests.

**Decision:** the current large Hero assessment card is approved for removal or replacement in a future implementation. It should be replaced with a compact selected-model/price module, not retained solely to satisfy obsolete presentation tests.

## Exact DOM/component chain

### Front Camera with selected model

1. `FrontCameraReplacementPage` calls `fetchRepairCatalog()`, builds candidates, and passes `hierarchy` to `CameraModuleRepairLandingPage`.
2. `CameraModuleRepairLandingPage` renders `main.repair-page-shell.repair-page-shell-narrow.repair-detail-page-shell`.
3. Inside `section.repair-hero.repair-detail-hero.relative.text-center` it renders: kicker, literal H1, subtitle, assessment card, then `SharedRepairHeroSelection`.
4. `SharedRepairHeroSelection` renders `SharedRepairSelectedDevice` for a valid server-derived selection, otherwise the model-selection anchor.
5. The hierarchy is a later sibling: `div.relative.z-10 > SharedRepairHierarchySections > SharedRepairHierarchyPresentation`.

The hierarchy presentation is client-interactive, but it is a sibling after the Hero. Neither it nor the Hero-selection component owns client selected-model state.

## Root cause

### Evidence-backed conclusion

**SOURCE-INFERRED:** the current camera Hero has no shared vertical stack wrapping the assessment and selected-device modules; they are independent, centered sibling blocks after the H1. This makes the Hero composition visually dominated by the large assessment card and leaves no single module responsible for the selected-model/price rhythm.

**SOURCE-INFERRED:** the inspected classes do not contain a source-level left alignment for either card. Both use `mx-auto`, `w-full`, `max-w-md`, and centered text; the Hero itself is centered by auto margins and inherited `text-align:center`. The H1 and cards therefore target the same horizontal center in source. The hierarchy is not an ancestor and cannot shift the Hero group.

**MANUAL QA OBSERVATION:** the browser still appears left-biased. The exact computed cause cannot be proven without a browser inspection of computed box dimensions, cascade order, viewport, and zoom. It is not supported to claim a definite flex/grid or nested-max-width offset from source alone.

The actionable architectural cause is therefore the fragmented Hero composition and obsolete assessment-first visual hierarchy, not a proven missing `mx-auto` utility.

## Is this actually a rendering/hydration bug?

**No, based on source evidence.** Camera selected identity is derived on the server before render. `SharedRepairHeroSelection` has no client state or fetch. The client-interactive hierarchy is rendered after the Hero and does not conditionally move Hero children. No SSR/client branch was found that would explain the observed horizontal placement.

Browser verification is still required to rule out an external computed-style/cascade or viewport-specific effect, but the current evidence does not support calling this a hydration bug.

## Why previous centering attempts failed

### `e2b9aa0` — `feat: align camera shared page UI`

This commit changed the assessment card from the earlier white rounded card to the current `mx-auto mt-6 flex w-full max-w-md flex-col items-center ... text-center` treatment, and changed surrounding content-card styling. It also added test selectors and a high-level visual-rhythm assertion.

It did not introduce a shared Hero content stack or alter the fundamental horizontal coordinate system: the old assessment card already had `mx-auto`, `w-full`, `max-w-md`, and `text-center`. The change was therefore a visual restyle and spacing change, not a proven correction for a parent-coordinate problem.

### `6a45660` — `feat: add camera shared selected-device flow`

This commit appended `SharedRepairSelectedDevice` as a second sibling after the assessment card and changed Camera hierarchy cards to selected-page query destinations. It did not group the assessment and selected panel under one layout owner, nor did it add selected model display-price data.

### Current uncommitted UX correction

The current correction replaces the direct Camera selected-device conditional with `SharedRepairHeroSelection`, which correctly adds the no-model anchor and removes duplicate booking authority. It preserves the same assessment-card sibling structure, intentionally because that task was scoped to CTA authority rather than Hero redesign.

## DO NOT TRY AGAIN

- Do not blindly add another `mx-auto` or `text-center`; both already exist on the relevant cards.
- Do not use negative margins, transforms, absolute positioning, or offsets to compensate for an unmeasured browser appearance.
- Do not center only a child while leaving Hero composition as unrelated sibling cards.
- Do not add client state, client fetches, or a second selected-model authority to solve a layout problem.
- Do not use the generic `Starting from $50` service card as selected-model price data.

## Correct future layout invariant

The Hero H1/subtitle and the compact selected-model module must be laid out by one predictable, centered Hero content stack. Each selectable module must have one explicit width contract (`w-full`, a shared max width, auto horizontal margins) and mobile/desktop behavior must be measured at the actual breakpoints.

The selected module is responsible only for selected identity, an already-derived display price when available, Book Repair, and Change model. It must not inherit the retired assessment card's visual weight or calculate Cart price.

## Select-your-model visual prominence

The current no-model anchor is an outlined white/blue utility link. The safest existing more-prominent pattern is the global `repair-primary-action` class used for established Hero calls to action. It supplies an inline-flex primary blue action, 44px minimum height, high-weight text, focus ring, hover elevation, and full-width mobile behavior through existing global CSS.

Future implementation should wrap or place that existing primary action in the Hero's already-centered action layout; it should not introduce new CSS merely to make the anchor visible.

## Manual QA acceptance criteria

### Desktop

- Model Hub link to a supported shared repair lands with the exact model selected; it never shows `Select your model` for that same canonical identity.
- Direct no-model entry shows a visually prominent real model-selection anchor and one usable hierarchy target.
- Clicking a model card goes directly to canonical Book Repair, with no selected-page reload intermediate step.
- Selected Hero shows exact `$X`, `From $X`, or no price according to the model-card display label; it never invents a generic price.
- Camera H1, compact model module, actions, and hierarchy share a visibly centered coordinate system at normal desktop zoom.

### Mobile

- The model-selection action and selected-device actions are full-width or otherwise clearly tappable.
- No horizontal overflow, clipping, visual offset, or focus-ring clipping occurs at narrow widths.
- Card click, Change model anchor, and canonical booking links remain usable without JavaScript-only selection state.

## Audit conclusion

The revised three-entry-path contract is feasible with existing canonical booking helpers and Phase 1 authority:

1. Model Hub → selected Shared Repair Page, selected device and model display price when known, then Book Repair.
2. Shared Repair Page model list → direct canonical Book Repair.
3. Direct organic no-model entry → prominent Select your model → model list → direct canonical Book Repair.

The Huawei P30 browser failure must be reconciled before declaring the Model Hub invariant safe in practice. Source confirms the requested pair is valid when present in the catalogue; it does not prove the runtime candidate input seen during manual QA.
